# Purpose

YouTube Auto Dark makes YouTube's own "Use device theme" setting live. When the OS flips between light and dark, open www.youtube.com tabs re-theme in place, with no reload, instead of waiting for the next load. A user who picked Dark or Light in YouTube's appearance menu is left alone. There is no popup and there are no settings.

# How YouTube themes itself (reverse-engineered from its `ytmainappweb` bundles, 2026-11)

- **Choice:** the `PREF` cookie (`f6` hex group) holds it. Flag 165 (`0x400`) means explicit dark and 174 (`0x80000`) explicit light; with neither set, the device theme applies (`isDeviceThemeChosen`)
- **Recording:** `ytd-app` listens to `prefers-color-scheme` (`onDeviceThemeChanged`) and only records flag 185 for the next server render. It never re-themes the open page. Its own theme switch (`onThemeSelected` -> `yt-dark-mode-toggled-action`) reloads with `themeRefresh=1`
- **Server render:** the server bakes the theme in: `<html dark>`, `:root` tokens for that theme (hashed `--t…` custom properties), and theme-resolved colors inside InnerTube data (`fontColor` runs)
- **Re-theming in place** (`src/features/live-theme/page/apply-theme.ts`), step by step:
  1. **Tokens:** `[light]`/`[dark]` are YouTube's token islands. No internal function changes the page's tokens (they are server-rendered), so the isolated script (`document/`) sets YouTube's own island attribute on `<html>`, where `html[dark]` variables such as live chat's resolve, and on `<body>`, because a few `:root:root` tokens outrank it on `<html>`. `DARK_THEME_TOKEN` (the DI token every signal component reads) is `() => html.hasAttribute("dark")`
  2. **Cached properties:** about 20 components copy `isDarkTheme` / `isDark` / `isDarkMode` / `pageDarkTheme` from `<html dark>` once (constructor/`attached`); they are re-set on each Polymer controller (`polymerController`)
     2b. **Masthead:** its `dark`/`isDarkThemeForced` come from the dark server shell, so outside theater mode (dark in either theme) they follow the theme. On a watch page in dark its "cinematic" background fades with scroll only on the next scroll event, so its own `updateMastheadBackgroundOpacity()` runs now; leaving dark, its own `resetBackground()` (keeping `watchPageScrollTop`). The searchbox's dark class is `forceDarkMode` (bound to masthead `dark`) `|| <html dark>`, recomputed only when `forceDarkMode` changes, so `dark` passes through the other value first
  3. **YouTube's own action:** `yt-dark-mode-toggled-action`'s handlers are called straight from YouTube's action router (`ytd-app`'s controller holds it as `actionRouter_`), skipping `ytd-app`'s own handler, which reloads
     2c. **Ambient mode:** the cinematics controller (Shorts, watch page) copies `<html dark>` into `isDarkModeEnabled` once at creation; it is found by shape on its owner and re-synced exactly as YouTube's `lVZ` does (`isDarkModeEnabled = ...; update()`)
  4. **Live chat:** live chat is its own server-rendered document with only its loaded theme's tokens. YouTube's `yt-dark-theme-action` / `yt-light-theme-action` make it toggle `<html dark>` (its `setGlobalDarkTheme`), which recolors nothing, so its own `ShadyCSS.styleDocument` gets the token values (read by the isolated script, sent with the switch) YouTube's page stylesheet declares in its `[dark]`/`[light]` island (read via CSSOM, never written). Nothing is ever reloaded
  5. **Palettes:** components with a `--yt-lightsource-*` palette re-run their own `dataChanged`, which picks the dark or light palette from `<html dark>`
  6. **Text:** `yt-attributed-string` resolves each run's `colorMap` with the theme at render, but skips data equal to its current data; it is re-rendered through its own signal setters (`rawProps.data()` / `setters.data`), once with every style run stripped, then with its data. View models that draw attributed text themselves (`yt-page-header-renderer`: a channel handle) are found the same way, as the nearest signal host above each colored `.ytAttributedStringHost` run. Bare `fontColor` runs the server baked for the old theme (the PREF cookie decides the server's theme) are translated with a dictionary learned from the page's own `colorMap`s - one table per target theme, kept for the page's lifetime (`ThemeColorPairs`). Attributed text nests attributed text (a collab byline carries its whole collaborators dialog in its tap command), so runs are found at any depth (JSON reviver, `nested-style-runs.ts`)
  7. **Late text:** while the page shows a theme other than the server's, a MutationObserver translates newly rendered attributed strings the same way (`late-text-repair.ts`). It is stopped before every switch, or it would translate that switch's own re-renders back
  8. **Panel content:** some content is baked by the server for the request's theme with no other version to translate to (a channel's link favicons: white for dark, gray for light; a Shorts sound page's byline gray; the request's theme comes from Chrome's `Sec-CH-Prefers-Color-Scheme`). Panel content (`ytd-engagement-panel-section-list-renderer`) loads through a `continuationItemRenderer` placeholder that the response replaces, so each placeholder is remembered as YouTube stamps it, against the nearest enclosing component with a `targetId` (an item section, a rich grid), first one wins (`section-refetch/`). On a switch each remembered placeholder is put back at the front of its container's `data.contents` (Polymer `unshift`; a placeholder sends its request when shown, which one at the end of a long grid is not), which sends its own request when stamped. The response either appends items in its place (`yt-next-continuation-data-updated`, then the stale items are spliced out) or reloads another slot such as a grid's header (`yt-reload-continuation-finish`, then only the pushed placeholder is spliced out). Both events are non-bubbling, fired on the container. The step is not awaited, so a response that never comes cannot hold the switch. Re-fetches of one container run one after another: two at once splice around each other's items and leave the content twice So that the wait shows no wrong color, once a panel's content has loaded it is requested for both themes (the request body's `userInterfaceTheme` decides the baked colors) and each bare color that differs joins the `ThemeColorPairs` the text step translates by (`learn-panel-colors.ts`) No timers anywhere: waiting is on YouTube's own events
  9. **Hover:** colors computed on pointer enter (a video card's tint and text) are recomputed by replaying leave and enter events on the hovered chain (`replay-hover.ts`)
- **Order:** the isolated script runs at document start and waits for YouTube's first `yt-navigate-finish`, so data the page loaded with stays colored for the server's theme, which is what steps 6-7 cover

# Layout

- `src/lib` - `theme/theme.ts` (Theme enum), `youtube/`, `zod.ts`
- `src/features/live-theme` - split by world: `document/` (isolated script: noticing the device theme change, reading `PREF` and the rendered theme, the theme attributes, hover replay, island tokens) and `page/` (MAIN script: one module per re-theme step that needs YouTube's JS objects, `components/` for the steps that re-theme particular components, `attributed-text/` for the text step, `section-refetch/`); `prefs/` reads `PREF`
- `dev-server`, `tools` - the dev server (`bun run dev` / `bun run dev:firefox`), two Rust crates adapted from youtube-downloader. `dev-server` is the library: watcher (`changes/`), the rebuild loop (`orchestrator.rs`) and the browser protocols (`driver/`: CDP for Chrome, WebDriver BiDi for Firefox). `tools` is the `devtool` binary: the warm WXT build worker, the isolated cloned profiles and the launch (Chrome for Testing with `--load-extension` on CDP port 9270; the installed Firefox on BiDi port 9272). On every save it rebuilds, reloads the extension (`chrome://extensions` / a temporary add-on install) and reloads the open YouTube tabs; the page scripts register listeners they never remove, so there is no in-place swap. The extension carries no dev-only permission, background script or re-injection code. Gates: `cargo clippy --all-targets` and `cargo test` in each crate
- A directory past about 8 files gets split into meaningful subfolders, and a file that mixes concerns gets divided

# Rules

- Page objects (components, controllers, windows) are validated with `z.looseObject` / `z.function()` schemas turned into type guards (`@/lib/zod-guard`), then used in place: a parsed copy would lose their identity and `this`. No `z.custom`
- Never reload anything, and never write CSS: only YouTube's own CSS (its island attributes) and its own JS
- The MAIN world is shared with YouTube's own scripts, so the extension adds no globals, patches no prototypes and no native functions, and writes only to the page objects a step names (a component's cached theme property, its `data`, the `<html>`/`<body>` island attributes). A message crossing into it carries a namespace of its own and a zod-validated payload, since page scripts can see and forge anything posted there
- Messages between worlds (the page's MAIN world, the isolated world, the background) go through [`@webext-core/messaging`](https://npm.im/@webext-core/messaging), with a `ProtocolMap` interface keyed by the members of one string enum (`[MessageType.X]: (data) => result`; one enum and one map for both the window and the extension messenger). Whatever needs only the DOM belongs to the isolated script (`document-worker.content.ts`, run at document start): it waits for YouTube's first `yt-navigate-finish` (when the body and the components exist), asks the background to run the MAIN script (`youtube-page.js`) with `scripting.executeScript({ world: "MAIN" })`, then watches `prefers-color-scheme`; on a switch it writes the theme attributes, tells the MAIN script (`APPLY_THEME`) and, once that has re-themed the components, replays hover. The injection resolves after the MAIN script has registered its handler, so there is no handshake. Injecting it with a `<script src>` tag instead fails in Firefox, where YouTube's CSP blocks a `moz-extension://` script; the extension API is not subject to the page's CSP. Only what needs YouTube's JS objects stays in MAIN, including the observers that read an element's component data as it is added
